## 公式資料

以下のCarbon資料はCarbon MCP `docs_search` で取得。Buttonは `code_search` で公式例も取得した。閲覧したローカルの `@carbon/react` は1.118.0、MCPのButton例の参照元はv11.117.0。将来実装時にはローカルの実際のAPIも照合する。

- [F1：Form — 必須・任意の表し方](https://carbondesignsystem.com/building-blocks/core/components/form/guidelines/#required)：多数が必須なら任意項目を、多数が任意なら必須項目を示し、扱いを統一する。
- [F2：Form — 配置・入力サイズ](https://carbondesignsystem.com/building-blocks/core/components/form/guidelines/#alignment)：標準フォームとfluidフォームで配置規則が異なる。標準入力は32／40／48px、fluidは64pxで、余白も同一規則ではない。
- [F3：Button — 有効／無効状態の色](https://carbondesignsystem.com/building-blocks/core/components/button/specifications/#primary-button-interactive-state-color)：通常とdisabledでラベル・背景のトークンを区別する。
- [F4：Progress indicator — アクセシビリティ](https://carbondesignsystem.com/building-blocks/core/components/progress-indicator/accessibility/#accessibility-considerations)：明確な短い名称と各手順の状態を伝える。
- [F5：File uploader — キーボード操作](https://carbondesignsystem.com/building-blocks/core/components/file-uploader/accessibility/#keyboard-interactions)：追加操作をTabで選びEnter／Spaceで実行し、各ファイルの削除操作へも到達できる。
- [F6：Notification — Inline](https://carbondesignsystem.com/building-blocks/core/components/notification/guidelines/#inline)：タスク中の操作の状態を、その文脈で通知する。[利用上の注意](https://carbondesignsystem.com/building-blocks/core/components/notification/guidelines/#when-to-use)では通知の多用を避ける。
- [F7：Data table — 行の密度](https://carbondesignsystem.com/building-blocks/core/components/data-table/guidelines/#header-and-row-height)：密度・複数行の内容に応じて行高を選ぶ。単純な行の目安を多項目編集カード全体の高さへそのまま適用しない。
- [F8：Accordion — 使わない場面](https://carbondesignsystem.com/building-blocks/core/components/accordion/guidelines/#when-not-to-use)：全内容を読む必要がある場合、一律に折り畳むと余分な操作になる。
- [F9：Typography — Utility／Body](https://carbondesignsystem.com/building-blocks/foundations/typography/type-sets/#utility-styles)：本文・ラベル・補足の役割に応じたタイプスタイルを使用する。
- [W1：W3C WAI — 関連する入力のグループ化](https://www.w3.org/WAI/tutorials/forms/grouping/)：見た目とコードの両方で入力群を関連付ける。fieldset／legend、または名前を持つgroupが方法となる。
- [W2：WCAG 2.5.8 — 最小ターゲットサイズ](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)：24×24 CSS pxが基準。間隔・インラインなどの例外があるため、寸法だけでは違反と断定しない。
- [H1：html2canvas — 対応CSS](https://html2canvas.hertzen.com/features)：`object-fit` は未対応の一覧に含まれる。これはCarbonの指針とは別の、出力処理の技術的制約。

## 優先順の改善案

### P1-1：PDF地図の縦横比を保持する

**観測・原因：** 元画像は1280×831（横／縦≒1.540）。画面では正常だが、PDF第2ページでは縦に伸びている。`src/styles.scss:267` の地図枠は高さ188mm、画像は幅・高さ100%と`object-fit:contain`。実測画像ボックスは約657.64×710.55px。`app-view.js:396` はhtml2canvasでページを画像化する。未対応のobject-fitへ依存しているため、画像が元画像比ではなく枠比で描画される。

**公式の指針：** H1はobject-fitを未対応としている。CarbonのトークンやGridの採用だけではこの問題は直らない。

**本件の判断・採用案：** PDF用に、画像の自然寸法と枠の内寸から `s=min(枠幅/元幅, 枠高/元高)` を計算し、幅・高さを同じ倍率で明示して中央配置する。画像読込完了後、すべてのPDF生成経路が使う共通処理で適用する。画面表示・準備済みPDF・プレビュー・保存／共有の入力契約を揃える。

**不採用：** 枠を横長固定にするだけ、画像を切り抜いて枠へ埋める、画面側のobject-fit指定だけを増やす。別比率の画像で再発し、地図端やルートが欠けるため。

**対象：** `app-view.js` の生成・寸法計算、`src/styles.scss` のPDF用地図、既存PDF出力の受入項目。

**将来の受入：** 今回の1280×831、縦長、正方形で生成PDFをレンダリングし、画像全体の比率誤差を1%以内とする（本件の受入値でありCarbon規定ではない）。枠外への切れ、円形マーカーの楕円化、注意書きの押出しがない。ブラウザ上のDOMだけで合格にしない。

### P1-2：「次へ」の見た目と操作状態を一致させる

**観測・原因：** YAMAPで「読み取り完了。行程21地点」と表示。`#step2-next.disabled` はfalse、実際に確認へ進める一方、`cds--btn--disabled` が残って文字・背景とも無効色。初期React JSXのdisabledと、後からDOMのdisabledを直接変更する処理の状態管理が分かれている。

**公式の指針：** F3は通常と無効の見た目を区別する。Buttonの公式例はkind／sizeの省略も使用しており、省略自体と今回の不整合は別問題。

**本件の判断・採用案：** 進行可否をReactのButtonへpropsとして渡す。既存処理との間に小さな状態通知口を設け、disabled・表示・進行条件を同一の値から更新する。PDF準備や追加管轄などDOMでdisabledを変えている他の操作も対象を確認する。

**不採用：** `cds--btn--disabled` をCSSで全体的に上書きする、常に青くする。本当に無効な状態まで有効に見える。Carbon内部クラスへの追加依存も避ける。

**将来の受入：** 未解析→解析中→成功→失敗→画像変更の各状態で、見た目・disabled・キーボード操作・案内が一致。現在の21地点では「次へ」が通常の主操作色で確認へ進む。

### P1-3：空の追加管轄欄を本当に非表示にする

**観測・原因：** 空の警察署・電話番号の3件目が既に見え、「管轄を追加」も表示される。要素は `form-grid form-grid--2 police-row is-hidden` だがcomputed displayはgrid。先にある `.is-hidden {display:none}` が、後の同じ詳細度の `.form-grid {display:grid}` に負けている。

**公式の指針：** F2の入力群の明確な構造、W1の関連入力のグループ化。空の3件目を隠すこと自体は本件の情報設計上の判断。

**本件の判断・採用案：** 非表示条件がフォームのレイアウトに上書きされないよう、管轄行の表示責務を明確にする。入力済みの2件だけを表示し、追加操作で次の1件を表示してその名前欄へフォーカスする。

**不採用：** 全管轄を一律に常時表示する。現在のデータでは不要な空欄と追加操作が重複し、確認すべき対象を増やす。

**将来の受入：** 2件入力済みでは3件目が画面・Tab順・アクセシビリティツリーに出ない。追加後は1件だけ表示され、入力済みの管轄を隠さない。

### P1-4：完了済みの手順を戻っただけで未開始にしない

**観測・原因：** 確認→基本情報へ戻ると、21地点と画像を保持していてもYAMAP／確認が「未開始・disabled」になる。`app-view.js:282` は現在の位置だけで完了・未開始を計算している。

**公式の指針：** F4は手順の状態を明確に伝える。完了条件や再訪条件そのものは製品側で定義する。

**本件の判断・採用案：** 現在位置と完了／有効性を別に持つ。データが有効な完了済み手順は直接再訪可能にする。画像を変更して解析結果が無効になった場合などは、その依存関係に応じて完了を取り消す。

**不採用：** 常に全手順を自由に開く。未入力・再解析待ちでも出力へ進める経路を作るため。

**将来の受入：** 確認→基本情報→確認でデータと完了表示を保持する。一方、必要入力の欠落・解析対象の変更時は不正な出力へ進まない。

### P2-1：確認と編集の情報密度を分ける

**観測：** 確認画面は約9442px。1地点カードが約293.6px、21件と間隔で約6400pxを使用する。掲載しない分岐も同じ大きさで、PDF操作までの移動が長い。開始・終了を比較する際にも中間の全編集欄を通る。

**公式の指針：** F7は目的に応じた密度を示す。F8は必読の内容を一律に折り畳むことを避ける。Carbonが「この画面は何px以下」と規定しているわけではない。

**本件の判断・採用案：** 通常は全21地点の「24時間の時刻・地点名・PDF掲載状態」を連続した一覧で読めるようにする。各地点の編集操作で時刻・地点名・掲載・休憩・削除を開く。削除を各カードの大きな常設操作にしない。「掲載」は「PDFに掲載」など出力への影響が分かる名称へ変更。休憩入力が後続時刻に反映されることを操作の近くに説明する。

**概要の再構成：** 山名・日付・出発／到着・所要時間・距離等を先頭の主情報へ。集合と連絡先は短いグループで照合できる形にする。長い元画像名一覧は任意展開に移し、必要時に対象画像を開ける参照へ。概要から各修正先に移動できるようにする。

**不採用：** 全地点を一律に閉じたAccordionへ置換、分岐を確認一覧から削除、最初の数件しか表示しない構成。照合漏れを増やす。固定PDFフッターも初手では採用しない。まず一覧を短くし、必要性を再評価する。採用する場合はフォーカスや内容の遮蔽を別途確認する。

**対象：** `src/App.jsx`、`app-view.js` の行程・概要描画、`src/styles.scss`。

**将来の受入：** 全地点・時刻を一覧のまま照合できる。編集前後で掲載選択・休憩計算・時刻順・追加削除・フォーカスを保持。393pxで本文の横スクロールが出ず、長い地点名の全文が読める。

### P2-2：画像を本当に読める拡大表示と、明確な操作名にする

**観測：** 「画像を拡大」のsummaryは高さ約12px。同じ名称が4件ある。Enterで開閉できるが、画像が幅約210pxのカード本文側に入るため細い。元画像一覧はファイル名を記録できている。

**公式の指針：** F5のキーボード操作、W2のターゲット寸法と例外、W1の分かる名称・グループ化を参照。12pxという高さだけではWCAG違反と断定しない。

**本件の判断・採用案：** 「ルート画像を拡大」「行程1画像を拡大」のように特定できる名前とし、サムネイル全体も同じ拡大操作にする。文字操作は少なくとも24px、設計上は32px以上の高さを目安にする。拡大領域はカード本文の列に制約せず、画面内の利用可能幅で表示。閉じる操作・フォーカス復帰を設計する。PCでの比較表示は実装時に別途確認する。

**不採用：** 小さな画像をobject-fitだけ変えて拡大と呼ぶ、アップロード画像をすべて常時巨大表示する。前者は読取に役立たず、後者は入力画面を再び長くする。

**将来の受入：** 4画像を名前で区別でき、画像内の時刻・地点を拡大して照合できる。Tab／Enter／Space、閉じた後のフォーカスを確認。ファイル追加ダイアログを開く試験と、アクセシビリティツリーに同名の追加操作が二重に出る件の切り分けも実施する。

### P2-3：基本情報と反復入力の意味を明確にする

**観測：** 基本情報の日時と行程編集の時刻はブラウザのネイティブUIで月／日／年・AM／PM表示。概要は日本語日付・24時間で表示される。集合場所の単一行入力は全文を同時に読めない。「氏名」「電話番号」、複数回現れる「分岐を削除」等は名称だけでは対象を区別できない。

**公式の指針：** F1の必須／任意の統一、F2のフォーム配置、W1の入力群の関連付け。ネイティブdate／timeの見た目をCarbonだけで24時間表示に強制できるとは扱わない。

**本件の判断・採用案：** 企画者・留守本部・管轄1／2を意味のある入力グループにする。繰り返す行程の操作名には「09:22 分岐」のように時刻も含める。多数が必須の基本情報では任意項目を示し、冒頭説明と揃える。集合場所は折返して内容を確認できる編集または補助表示を設ける。行程一覧の通常表示は24時間で固定し、編集時のネイティブUIの差と区別する。

**不採用：** 学籍番号の形式を推測して独自制限する、日付・時刻を見た目だけのために全面的な自作ピッカーへ変更。業務ルールの根拠や実機検証がなく、入力の失敗を増やすため。

**将来の受入：** 入力や操作の対象を名称・グループで特定できる。長い集合場所を確認でき、元データ・概要・PDFの時刻と日付が一致する。

### P2-4：ユーザー指定の重複見出し・説明2文を削除する

**指定内容：** 画面先頭の大見出し「登山計画書」を削除。YAMAP冒頭の「選択した画像は外部の画像解析サービス（AI）に送信して読み取ります。読み取り後も内容を確認して修正できます。」を削除。

**公式の指針：** F9は情報の役割に応じた文字階層を用いる。これらの特定文言を削除せよというCarbon公式の規定はない。

**本件の判断・採用理由：** ユーザーの明示指定として採用。ヘッダーの製品名と各手順名を情報の軸にして上部の重複を減らす。YAMAPの最初の1文は画像枚数の指示として扱う。実装時は各手順の見出しをページの主見出しとして成立させ、現在の `step-heading-*` のフォーカス先IDを保持する。見出し要素を変える場合は対応するスタイルのセレクタも更新する。

**不採用：** PDF内の「○○登山計画書」まで削除、削除した見出しの余白だけ残す、見出し構造を失う実装。指定の画面要素とPDF表題を混同しない。

### P3：余白・文字階層と出力PDFのアクセシビリティを仕上げる
